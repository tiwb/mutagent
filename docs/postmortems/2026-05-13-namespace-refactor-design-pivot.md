# Namespace 数据层重构 — 从 DTO 到"对象即数据"的设计转向

**日期**：2026-05-13
**主题**：一次在设计阶段被用户挑战触发的方向回退，及其方法论启示
**相关 spec**：`refactor-namespace-describe-api.md`

## TL;DR

本次复盘记录一次**设计阶段**（未进入实施）发生的方向回退：
"DTO + 查询方法" 路线 → "对象引用 + 纯函数" 路线。回退是被用户一句
「不管现有设计，你是否有更合理的设计方案？」触发的。

核心教训：**接手已有 spec 时，AI 容易被文档已经写得完整这一表象锚定，
默认"设计是给定前提，我只补实施方案"，从而跳过了"这个抽象是不是必要"
的根本追问**。

## 时间线

| 时刻 | 事件 |
|------|------|
| T0 | 用户让 AI 看两份 spec：`refactor-namespace-describe-api.md`（已写 170 行 DTO 方案）和 `feature-mcp-schema-help-display.md`（下游，在等重构落地） |
| T1 | AI 第一轮：通读两份 spec + 关键代码，定位"现有方案缺实施方案章节"，准备把 Q1–Q4 升格为 DECIDED、补 Phase R1/R2/R3 清单 |
| T2 | 用户追问：「不管现有设计，你是否有更合理的设计方案？」 |

| T4 | 用户认可新方向，让 AI 重写 spec |
| T5 | AI 重写 spec，三个 Q 按建议落定，推进到 🔄 实施中，生成 R1–R4 清单 |

**关键转折点在 T2**。如果用户没主动问这一句，AI 会顺着 DTO 路线把实施清单
写出来，方向错误要等到实施一半甚至全部完成、下游 iter 接入时才会暴露。

## 起源

需求本身是明确的：消除 4 条 namespace 反查路径（help / Settings Panel /
share / list_tools_metadata）中的重复代码。下游 `feature-mcp-schema-help-display`
的 iter2 / iter3 / Phase 2b 在等这个重构落地。

现有 spec（v0）的设计方案：

- 定义 `FunctionDescr` / `ParamDescr` / `NamespaceDescr` 三个 TypedDict
- 在 `SandboxApp` 上加 `list_namespaces()` / `describe_namespace()` / `describe_function()` 三个方法
- `share.py::_describe_function` 提升为通用公开 API
- 所有消费者改为从 dict 读数据

spec 已完成 80%，只差"实施方案"章节。Q1–Q4 都已经有了"建议"，就差一个
DECIDED 标签。

## 第一轮 AI 的工作方式（反面样本）

```
读 spec → 核对代码现状 → 找"缺什么" → 补实施方案
```

AI 做了这些事：
- 核实每个消费者的代码现状
- 检查 Q1–Q4 建议的合理性
- 识别出 "spec 没明确消费者怎么拿 raw schema"（Q2 的小缺口）
- 准备补 Phase R1/R2/R3 清单、snapshot 回归策略、风险点

AI 没做这件事：
- **问一句"整个 DTO 路线本身是不是必要"**

当时 AI 的内部逻辑是：设计已经过 📝 设计中阶段，Q 都已经有建议，文档这么
完整说明方向已经论证过，我只需要把实施方案补齐。

**这是锚定效应的典型表现**：文档的完整度被误读为"设计的正确性"。

## 用户挑战后识别出的过度设计

用户的一句追问把 AI 从"完善者"模式推回"设计者"模式。重新审视后，原方案
有三层过度设计：

### 过度设计 #1：把伪重复也当重复

v0 spec 的"重复代码清单"列了 5 项。重新按"是否需要数据层统一抽象"分类：

| 编号 | 原列项 | 实际分类 |
|------|--------|---------|
| 1 | 函数签名提取 | 伪重复（`format_callable_signature()` 已收敛） |
| 2 | docstring 提取 | 伪重复（一行代码 `inspect.getdoc(fn)`） |
| 3 | Namespace 列表遍历 | 真重复 |
| 4 | 连接状态展示 | 渲染层重复（数据已统一） |
| 5 | 参数表生成 | 真重复 |

真重复只有 2 项。v0 为了 2 项真重复 + 1 项渲染层重复，引入了数据层 DTO +
3 个查询方法 + dict 映射层。

### 过度设计 #2：把序列化器误认为查询 API

`share.py::_describe_function` 是为 JSON-RPC 跨进程传输服务的，天然需要返回
dict。v0 把它"提升为通用 API"的决定忽略了一个关键事实：**跨进程和同进程对
数据载体的需求根本不同**。

证据线索藏在 iter1 的修复里：iter1 为了让 `_MISSING` sentinel 跨 JSON-RPC
不丢身份，引入了 `default_missing` 标记位。这是一种典型的**"为对抗序列化
损失而引入的复杂度"**——只有跨进程消费者才需要承担。如果让所有消费者统一
走 DTO，同进程消费者也要被迫处理 `default_missing` / `default_repr` /
`default` 三种默认值形态，本来直接访问 `p.default is _MISSING` 一行能解决。

### 过度设计 #3：在已有数据模型之上套 DTO

Python 的 callable 对象本来就承载了完整信息：

```
fn.__doc__ / fn.__signature__ / fn.__name__
fn._mcp_input_schema / fn._mcp_description
```

`Namespace` / `MergedNamespaceView` 也已经有完整的数据接口。v0 在这之上再铺
一层 `FunctionDescr` / `ParamDescr` / `NamespaceDescr`，本质是把对象降级为
dict。这和项目的 mutobj 哲学（对象作为一等公民）方向相反。

## 识别过度设计用到的原则

### 原则 1：真重复 / 伪重复 / 渲染重复 三分法

列"重复清单"前先分类：

- **伪重复**：已被某个公共函数收敛，调用方式看起来各异但本质是同一入口
- **渲染重复**：数据本身是统一的（如 `ns.connection_state` 字符串），只是
  各渲染端的映射各自一套
- **真重复**：多处代码实际在从原始字段手工拼装同一类结构

三类的治疗方案不同：

- 伪重复 → 不动（已经收敛了）
- 渲染重复 → 抽**纯函数**（数据映射），不是 DTO
- 真重复 → 抽**公共工具**（可以是函数、内部 helper，不一定是 API）

v0 方案把三类一视同仁用一个 DTO 层解决，是过度抽象。

### 原则 2：查询 vs 序列化 职责分离

- **序列化器**：对象 → 字节 → 线 → 字节 → 对象，双向管道，存在理由是跨边界
- **查询接口**：同进程消费者拿数据视图，存在理由是数据封装

两者的具体差异：

| 维度 | 序列化器 | 查询接口 |
|------|---------|---------|
| 返回载体 | 必须是可序列化的 dict/bytes | 可以是对象引用 |
| 信息损失 | 需要显式补偿（如 `default_missing`） | 无损失（对象就是源） |
| 消费者职责 | 要理解序列化协议 | 直接用 Python 对象协议 |
| 演进性 | 跨版本兼容约束强 | 跟随对象模型自然演进 |

合并两者的代价：同进程消费者被迫承担跨进程协议的包袱。

### 原则 3：对象即数据（Object-as-Data）

Python 里，如果一个对象已经承载了全部需要暴露的字段（通过 property 或公开
属性），**不要再铺一层 DTO**。DTO 是给跨边界场景准备的（跨进程、跨语言、
API 边界）。

判据：

- 消费者在同进程 → 用对象引用
- 消费者要序列化 → 加专用序列化器（和查询 API 分开）

### 原则 4：信号灯原则

当一个设计需要一连串"对抗某种损失/副作用"的 patch（iter1 的
`default_missing` 就是典型），这些 patch 往往指向**设计方向本身**的问题，
而不是需要继续 patch 下去。

识别方法：阅读下游 iter / bugfix 的修复描述。如果修复文案里反复出现
"跨 xxx 丢失 yyy"、"为此需要补充 zzz 字段"，就是信号。

v0 spec 的 Q2 也有类似信号：「消费者如何拿到 raw schema？」这个问题在 v0
框架下需要在 `FunctionDescr` 加旁路字段才能回答。在新方案下这个问题根本
不存在——消费者直接访问 `fn._mcp_input_schema`。一个问题**在另一个设计下
自动消失**，是方向问题的强信号。

### 原则 5：最小手术 / 对抗抽象通胀

消除真重复时，先尝试最小手术：

1. 抽一个内部 helper 函数
2. 加一两个薄查询方法
3. 实在需要结构化时才加 DTO

v0 直接跳到第 3 步。新方案的 M1（合并收集逻辑）和 M3（连接状态纯函数）
就是第 1 步，M2（`iter_namespaces` / `get_namespace`）是第 2 步。整个重构
没有第 3 步。

## 第一轮为什么没识别出来

反思 AI 的认知路径：

| 认知偏差 | 具体表现 |
|---------|---------|
| **锚定效应** | spec 170 行、Q1–Q4 都有建议 → 误读为"方向已论证" |
| **任务框架锁定** | 用户说"完善设计和实施方案" → 自动把"设计"视为给定前提 |
| **补缺思维** | 专注找"缺什么"（缺 Phase 清单、缺测试策略），没问"多了什么" |
| **对齐下游的惯性** | 下游 iter2/iter3 的前置依赖已经写好 → 假设整条链路方向正确 |

这些偏差合在一起，让 AI 把"完整的文档"当成了"正确的设计"。

## 未来工作方式

### 做法 1：接手现有 spec 时必须问的一个问题

在读完 spec + 现有代码后，**在动笔前**问自己一遍：

> 如果我完全不看这份 spec，只看需求和代码现状，我会设计成这样吗？

如果答案是"不一定"，就应该向用户呈现**至少一个替代方案**再推进。即使
最后还是选原方案，也完成了方向论证。

这个追问 T0-T1 之间应该发生。当时没有发生，是因为 AI 跳过了"独立重新设计"
这一步，直接进入"评估现有设计 → 补缺"。

### 做法 2：按"真/假/渲染重复"分类再决定抽象层次

面对"消除重复代码"类需求时，第一步不是设计抽象，而是**分类重复**：

1. 列所有重复点
2. 每一项标上 { 伪重复 / 渲染重复 / 真重复 } 中的一类
3. 按分类决定治疗方案（不抽 / 纯函数 / 公共工具）
4. 统计真重复数量 —— 如果只有 1-2 项，警惕 DTO 路线

### 做法 3：读下游 iter / bugfix 找信号灯

新设计读完主 spec 后，**必须读一遍下游 iter / bugfix 的修复描述**。关注词：

- "丢失"、"跨 xxx 损失"
- "为此新增字段"、"兼容层"
- "反推"、"解析"（尤其是反向解析已格式化的字符串）

这些是设计方向的信号灯。本次 iter1 的 `_MISSING` 修复就是一个典型，AI 第一轮
读了 iter1 但没把它作为"方向信号"处理，只当作"既成事实"消化掉。

### 做法 4：用户挑战要触发"从零重设计"模式

当用户说出这类话：

- 「不管现有设计……」
- 「有没有更合理的方案？」
- 「是不是过度了？」
- 「我觉得应该……」（CLAUDE.md 性能调试流程也提过）

**立刻停止补丁模式，进入从零设计模式**。用户主动发起挑战，往往是他自己对
方向已经有怀疑。这种信号的优先级高于"继续推进当前任务"。

### 做法 5：序列化需求独立看

项目里有跨进程 / 跨边界场景时（本项目的 pysandbox sharing、mutbot 的 MCP
协议），它们的数据载体必然是 dict。**不要把跨边界的数据模型反哺到同进程
查询 API**。

具体识别：看到 spec 里写 "提升 xxx 为通用 API"，而 xxx 原本是跨进程
序列化器，就要追问"跨进程的复杂度（sentinel / 兼容层 / 版本协商）是否
应该让同进程消费者承担"。答案通常是否定的。

## 经验提炼

### 可复用的判别法

**"抽象必要性三问"**——接手任何"统一 / 抽象 / 重构"类需求时问：

1. **真重复几项？** 如果 ≤ 2 项，倾向于最小手术（helper / 纯函数）而非 DTO
2. **消费者跨进程吗？** 如果全同进程，用对象引用；如果只有个别跨进程，
   给跨进程消费者专用序列化器，不污染查询 API
3. **数据已经在对象上了吗？** Python 里 callable / class 已经是数据模型，
   再套 DTO 前先问"对象接口已经够用吗"

### 可复用的 pattern 警告

- **"把 A 提升为 B 的通用 API"**：A 原本为啥存在？如果 A 是为某个特殊场景
  （跨进程、协议适配、序列化）而生，提升通常会把特殊场景的复杂度泄露给
  所有消费者
- **"数据模型 = 序列化格式"**：如果两者同构，说明数据模型是按序列化需求
  设计的，不是按消费者需求设计的
- **"需要反向解析格式化字符串"**：永远是方向错误的信号

### 对 SDD 流程的建议

当前 SDD 规范的 📋 → 📝 → 🔄 → ✅ 阶段假设"设计阶段结束后方向已论证"。
本次事件说明 **📝 设计中阶段结束前应该有一道"方向独立性检查"**：

> 在生成实施清单之前，AI 独立写一段 50 字以内的"如果我重新设计会怎么做"，
> 和 spec 方向对比，若有偏差主动呈现给用户。

这个检查不是工作量很大，但能在最便宜的阶段（还没进实施）捕捉方向问题。

可以把这条加进 `sdd` skill 的"设计阶段"规则。

## 附录：这些"原则"的出处定性

复盘写完后被追问：这些原则有出处吗？是哪里来的方法论？诚实回答记录于此，
避免未来被当成"权威引用"误用。

**结论**：大部分不是引用现成方法论，是本次复盘现场提炼的说法。只有少数概念
能对应到既有文献。

### 有既有来源的

| 文档里的说法 | 真实出处 |
|---|---|
| 锚定效应 | Kahneman & Tversky 1974，认知心理学经典，非软件方法论 |
| 对抗抽象通胀 / 过度设计警告 | 精神源自 XP 的 **YAGNI**（Kent Beck）和 **Rule of Three**（Martin Fowler *Refactoring*）。"真重复 ≤ 2 项 → 不抽 DTO" 本质是 Rule of Three 的变体 |
| DTO vs 对象引用 | 对应 DDD（Eric Evans 2003）"anemic domain model" 反模式讨论；Martin Fowler *LocalDTO* 明确说同进程不要用 DTO |
| 最小手术 | Fowler *Refactoring* 的 "smallest step" 原则 |
| 序列化器 vs 查询 API 职责分离 | 六边形架构 / Clean Architecture "边界处做转换" 的精神 |

### 现场生造的（没有出处）

以下措辞是本篇复盘**当场总结**出来的，不是引用既有术语：

- **真 / 伪 / 渲染 重复 三分法** —— 现造分类，无既有术语对应
- **信号灯原则** —— 现造比喻，指 "下游 iter 反复打补丁说明方向错"；精神上
  接近 *Refactoring* 的 "code smell"，但 "信号灯" 是临时命名
- **对象即数据 (Object-as-Data)** —— 这个名字容易和 Clojure 社区的
  *data-oriented programming*（Yehonathan Sharvit）混淆，但方向相反（那本书
  反对 OO 封装、提倡 plain data；这里是反过来，用 Python 对象本身当数据载体）。
  **不宜当作术语引用**，只是本次复盘的口号
- **抽象必要性三问** —— 现场总结的 checklist，非既有方法论
- **补缺思维 / 任务框架锁定** —— AI 自述的认知偏差命名，非既有术语

### 一句话定性

本复盘是 **"以 YAGNI / Rule of Three / DDD 反贫血模型为底色，现场针对本次
案例提炼的操作化口诀"**。

"原则 1~5" 的**精神**能在软件工程经典文献里找到对应，但**具体措辞**大部分
是 AI 当场为讲清楚本次事件造的。引用时建议：

- 保留精神（YAGNI、边界处转换、Rule of Three、anemic domain model 反模式）
- 自造命名（"三分法"、"信号灯"、"对象即数据"）仅作本文内速记使用，**不要
  外推为通用方法论**
- 若要进 `sdd` skill 作为稳定规则，应换成社区已有术语，减少后人查无此源的困惑
